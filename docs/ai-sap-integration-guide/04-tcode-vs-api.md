# Part 4：VA01 / VA02 / VA03 与 API 的关系（VA01 / VA02 / VA03 と API の関係）

## 4.1 三个事务代码是什么（3 つのトランザクションコードとは）

| 事务代码<br>トランザクションコード | 名称 | 作用（機能） |
|---|---|---|
| VA01 | Create Sales Order | 在 SAP GUI 里手工创建销售订单的经典界面<br>SAP GUI 上で手動で販売オーダーを作成するクラシックな画面 |
| VA02 | Change Sales Order | 修改已存在的订单<br>既存のオーダーを変更する |
| VA03 | Display Sales Order | 只读查看订单<br>オーダーを参照専用で表示する |

SAP 顾问习惯从这些事务代码理解业务，是因为**几十年来 SD 顾问的培训、文档、客户培训材料都基于这套屏幕结构**——VA01 的屏幕流（Header 数据 → Item 概览 → Item 明细 → Schedule Line → Pricing 明细）直接对应了 Sales Order 的数据模型层次。理解 VA01 的屏幕逻辑，本质就是在理解 Sales Order 的数据结构和业务规则触发时机（比如切换 Item 明细屏幕时会触发一次 ATP 检查）。

SAP コンサルタントがこれらのトランザクションコードを通じて業務を理解する習慣があるのは、**何十年にもわたって SD コンサルタントのトレーニング、ドキュメント、顧客向けトレーニング教材がすべてこの画面構造に基づいてきた**からです——VA01 の画面フロー（Header データ → Item 概要 → Item 明細 → Schedule Line → Pricing 明細）は、Sales Order のデータモデル階層に直接対応しています。VA01 の画面ロジックを理解することは、本質的には Sales Order のデータ構造とビジネスルールがトリガーされるタイミング（例えば Item 明細画面に切り替えると ATP チェックがトリガーされる）を理解することです。

## 4.2 "VA01 手工创建" vs "程序通过 API 创建"（「VA01 での手動作成」 vs 「プログラムによる API 経由の作成」）

### 相同点（共通点）

- **底层调用的业务逻辑是同一套**：无论是 VA01 的屏幕操作，还是 OData API / BAPI 调用，最终都会走到 SAP 内核的同一批业务逻辑函数（Function Module），执行同样的 Sales Area 校验、Pricing 计算、Credit Check、ATP。

  **内部で呼び出されるビジネスロジックは同一のもの**：VA01 の画面操作であっても、OData API / BAPI 呼び出しであっても、最終的には SAP カーネル内の同じビジネスロジック関数群（Function Module）に到達し、同じ Sales Area チェック、Pricing 計算、Credit Check、ATP を実行します。

- **数据模型相同**：Header/Item/Schedule Line 的表结构（VBAK/VBAP/VBEP 等，⚠️ 具体表名以系统版本为准）是共享的。

  **データモデルは共通**：Header/Item/Schedule Line のテーブル構造（VBAK/VBAP/VBEP など、⚠️ 具体的なテーブル名はシステムバージョンにより確認が必要）は共有されています。

- **业务规则（如必填字段、状态检查）是相同的**，因为这些规则通常配置在 Customizing（SPRO）里，是全局生效的，不会因为走 GUI 还是 API 而不同。

  **ビジネスルール（必須項目、ステータスチェックなど）は同一**です。これらのルールは通常 Customizing（SPRO）で設定され、グローバルに有効であり、GUI か API かによって変わることはありません。

### 不同点（相違点）

| 维度<br>観点 | VA01（GUI） | API（OData/BAPI） |
|---|---|---|
| 交互性<br>インタラクティブ性 | 屏幕间可以来回切换、边填边看系统提示（如缺字段会高亮）<br>画面間を行き来でき、入力しながらシステムのメッセージを確認できる（不足項目はハイライトされるなど） | 一次性提交结构化数据，没有"边填边看"的交互过程<br>構造化データを一括で送信し、「入力しながら確認する」というやり取りはない |
| 默认值来源<br>デフォルト値の出所 | 很多默认值来自用户的 GUI Parameter ID / 上次输入记忆<br>多くのデフォルト値はユーザーの GUI Parameter ID や前回の入力履歴に由来する | 完全依赖调用方显式传入或后端主数据推导，没有"记住上次输入"这种便利<br>呼び出し側が明示的に渡すか、バックエンドのマスタデータから導出するしかなく、「前回の入力を覚えている」という便利さはない |
| 中间态确认<br>中間状態の確認 | 用户可以在提交前反复查看、修改多个屏幕<br>ユーザーは送信前に複数の画面を何度も確認・修正できる | 需要调用方自己实现"预检查/模拟"来达到类似效果（比如先调用 Pricing 模拟接口）<br>呼び出し側が「事前チェック／シミュレーション」を自ら実装して同様の効果を得る必要がある（例えば先に Pricing シミュレーション API を呼び出すなど） |
| 错误反馈<br>エラーフィードバック | 屏幕上逐字段高亮报错，用户可以立刻改<br>画面上で項目ごとにエラーがハイライトされ、ユーザーはすぐに修正できる | 返回结构化错误码/消息，需要调用方解析并转成用户可读文案<br>構造化されたエラーコード／メッセージが返され、呼び出し側がそれを解析してユーザーが読める文言に変換する必要がある |
| 权限模型<br>権限モデル | 基于 SAP GUI 用户角色（Authorization Object，如 V_VBAK_VKO）<br>SAP GUI のユーザーロール（Authorization Object、例：V_VBAK_VKO）に基づく | 同样基于 Authorization Object，但通常通过技术用户或 OAuth Principal Propagation 传递身份<br>同じく Authorization Object に基づくが、通常はテクニカルユーザーまたは OAuth Principal Propagation によってアイデンティティを伝播する |
| 批量/自动化<br>一括処理／自動化 | 不适合批量，一次一单<br>一括処理には向かず、1 回につき 1 件のオーダー | 适合程序化批量调用<br>プログラムによる一括呼び出しに適している |

### 关键澄清："API 不是简单地模拟点击 VA01"（重要な補足：「API は単に VA01 のクリックをシミュレートしているわけではない」）

这是一个常见的误解，需要纠正：

これはよくある誤解であり、正しておく必要があります：

1. **VA01 是"人机交互界面"，API 是"程序对内核业务逻辑的直接调用"**，两者都是内核逻辑的"客户端"，谁也不是谁的模拟。API 并不是通过脚本自动点击 GUI 按钮实现的（那是 RPA 的做法，效率低、脆弱，企业级项目基本不用这种方式）。

   **VA01 は「人とのインタラクション画面」であり、API は「プログラムによるカーネルのビジネスロジックへの直接呼び出し」**です。両者はいずれもカーネルロジックの「クライアント」であり、どちらかがどちらかをシミュレートしているわけではありません。API はスクリプトで GUI のボタンを自動クリックして実現しているのではありません（それは RPA のやり方であり、効率が低く脆弱なため、企業向けプロジェクトではほとんど採用されません）。

2. **API 的字段集合和 GUI 的字段集合不完全一一对应**：GUI 屏幕上有很多是"辅助展示"或"多屏幕分步填写"的字段，API 通常需要在一次请求里把所有必要数据结构化地准备好（比如 Deep Insert 一次性带 Header+Item）。

   **API のフィールド集合と GUI のフィールド集合は完全には一対一で対応しません**：GUI 画面には「補助的な表示」用や「複数画面にまたがる段階的な入力」用のフィールドが多くあります。API は通常、1 回のリクエストで必要なデータをすべて構造化して用意する必要があります（例えば Deep Insert で Header と Item を一度に渡すなど）。

3. **GUI 里很多"隐式默认值"（用户参数记忆、SU3 Parameter ID 默认值）在 API 调用中不存在**，必须由调用方显式提供或后端逻辑推导，这也是为什么"缺失参数判断"（Part 2 第二步）在 AI+API 项目里特别重要——你没有 GUI 那种"人在回路里随手补全"的便利。

   **GUI にある多くの「暗黙のデフォルト値」（ユーザーパラメータの記憶、SU3 Parameter ID のデフォルト値）は API 呼び出しには存在しません**。呼び出し側が明示的に提供するか、バックエンドロジックで導出する必要があります。これが、AI+API プロジェクトにおいて「不足パラメータの判定」（Part 2 のステップ 2）が特に重要である理由でもあります——GUI のように「人間がその場で補完してくれる」という便利さがないのです。

4. **两者共享同一套业务规则引擎**，所以不存在"API 创建的订单校验更松"这种情况——如果 Credit Check 配置为强制检查，无论走 GUI 还是 API 都会触发。

   **両者は同じビジネスルールエンジンを共有している**ため、「API で作成したオーダーの方がチェックが緩い」ということはあり得ません——Credit Check が強制チェックとして設定されていれば、GUI 経由でも API 経由でも必ずトリガーされます。

## 4.3 项目中你需要记住什么（プロジェクトで覚えておくべきこと）

- 理解 VA01 的屏幕结构（Header/Item/Schedule Line/Pricing）能帮你更快理解 API 的数据结构，两者是同源的。

  VA01 の画面構造（Header/Item/Schedule Line/Pricing）を理解しておくと、API のデータ構造をより早く理解できます。両者は同じ源から来ています。

- API 调用没有 GUI 那种"边填边看、系统帮你记住默认值"的便利，所以 AI+后端必须自己承担"参数补全和预校验"的职责。

  API 呼び出しには GUI のような「入力しながら確認でき、システムがデフォルト値を覚えてくれる」という便利さがないため、AI＋バックエンドが自ら「パラメータの補完と事前チェック」の役割を担う必要があります。

- 不要把"调用 API"简单理解为"模拟点了几下鼠标"，它是对同一套业务内核的另一种客户端接入方式。

  「API を呼び出す」ことを単に「マウスを何回かクリックしたことをシミュレートしている」と単純に理解してはいけません。それは同じビジネスカーネルへの別の形のクライアントアクセス方法です。

- 与 SAP 顾问沟通时，用 VA01 的屏幕结构作为共同语言（"这个字段对应 VA01 哪个屏幕的哪个字段"）能极大提高沟通效率。

  SAP コンサルタントとコミュニケーションする際は、VA01 の画面構造を共通言語として使う（「このフィールドは VA01 のどの画面のどのフィールドに対応するか」）ことで、コミュニケーション効率を大幅に高めることができます。
