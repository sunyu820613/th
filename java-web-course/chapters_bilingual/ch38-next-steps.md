# 第 38 章　学完之后：后续学习路线 ／ 第38章　学び終えた後：今後の学習ロードマップ

到这里，这本教程的正文就全部结束了。这一章不再是"学新知识"，而是帮你盘点一下"你现在手里有什么"，以及"接下来往哪个方向走"。

> 🇯🇵 ここまでで、このチュートリアルの本編はすべて終了です。この章はもう「新しい知識を学ぶ」章ではなく、「あなたが今、何を手にしているか」を棚卸しし、「次にどの方向に進むか」を考える手助けをするものです。

## 你现在已经具备的能力 ／ あなたが今身につけている能力

如果你是从第 1 章一路做到第 37 章的最终项目，现在你应该已经能够独立完成这些事：

> 🇯🇵 もしあなたが第1章から第37章の最終プロジェクトまで一通りやり遂げたなら、今ではもう次のことを独力でこなせるはずです。

- 独立搭建一个 Spring Boot 项目，看懂 `pom.xml`、`application.yml`、`@SpringBootApplication` 分别在做什么。<br><span class="ja-inline">🇯🇵 独力で Spring Boot プロジェクトを構築し、`pom.xml`、`application.yml`、`@SpringBootApplication` がそれぞれ何をしているのか理解できる。</span>
- 设计一个符合 RESTful 规范的接口（资源式 URL + 标准 HTTP 方法），并用 `@RestController` 把它实现出来。<br><span class="ja-inline">🇯🇵 RESTful（リソース指向の URL ＋標準的な HTTP メソッドで設計する API のスタイル）に沿った API を設計し、`@RestController` で実装できる。</span>
- 用 Controller-Service-Mapper 三层结构组织代码，说清楚每一层各自的职责边界。<br><span class="ja-inline">🇯🇵 Controller-Service-Mapper の三層構造でコードを整理し、各層の責務の境界をきちんと説明できる。</span>
- 用 MyBatis-Plus 完成单表甚至多表关联场景下的增删改查，包括基础分页。<br><span class="ja-inline">🇯🇵 MyBatis-Plus を使って、単一テーブルはもちろん複数テーブル関連のシーンでも CRUD（作成・参照・更新・削除）を実装でき、基本的なページネーション（一覧を複数ページに分けて返す仕組み）も扱える。</span>
- 用 DTO 把对外暴露的数据和数据库实体隔离开，用 `@Valid` 做参数校验，用 `@RestControllerAdvice` 做统一异常处理。<br><span class="ja-inline">🇯🇵 DTO（Data Transfer Object、外部とやり取りするためのデータの入れ物）を使って外部に公開するデータとデータベースの実体（Entity）を分離し、`@Valid` でパラメータのバリデーションを行い、`@RestControllerAdvice` で例外を一括処理できる。</span>
- 看懂并能画出"浏览器发请求到收到 JSON 响应"这条完整调用链，并且能对照任意一个 Spring Boot 项目的真实代码把这条链路讲清楚。<br><span class="ja-inline">🇯🇵 「ブラウザがリクエストを送信してから JSON レスポンスを受け取るまで」の一連の呼び出しの流れを理解し、図に描くことができ、実際の Spring Boot プロジェクトのコードと照らし合わせてその流れを説明できる。</span>
- 用 `@Transactional` 保证一组数据库操作的一致性。<br><span class="ja-inline">🇯🇵 `@Transactional`（トランザクション、一連のデータベース操作を「全部成功」か「全部失敗して元に戻す」かのどちらかに保証する仕組み）を使って、一連のデータベース操作の一貫性を保証できる。</span>
- 给 Service 层和 Controller 层分别写最基础的自动化测试，理解单元测试和集成测试的区别。<br><span class="ja-inline">🇯🇵 Service 層と Controller 層それぞれに最も基本的な自動テストを書くことができ、単体テストと結合テストの違いを理解している。</span>
- 面对一个报错（404/400/500/连接失败/Bean not found），有基本的排查思路，而不是完全懵。<br><span class="ja-inline">🇯🇵 エラー（404/400/500/接続失敗/Bean not found）に直面したとき、まったく手も足も出ないのではなく、基本的な調査の道筋を持てる。</span>

这已经不是"玩具级别"的能力了——你现在能看懂、也能自己写出一个结构完整、能真实运行的后端项目雏形。

> 🇯🇵 これはもう「おもちゃレベル」の能力ではありません——あなたは今、構造が整った、実際に動くバックエンドプロジェクトの原型を読み解くことも、自分で書くこともできるのです。

## 接下来可以深入的方向 ／ 今後さらに深められる方向

本教程的定位是**零基础入门**，目标是让你从"完全不会"走到"能独立搭建一个结构完整的项目"。但企业级项目还有很多本教程刻意没有展开的内容，属于"学完这本教程之后"的进阶方向：

> 🇯🇵 本チュートリアルの位置づけは**ゼロからの入門**であり、目標は「まったくできない」状態から「構造の整ったプロジェクトを独力で構築できる」状態まで導くことです。しかし、実際の企業プロジェクトには、本チュートリアルがあえて掘り下げなかった内容がまだたくさんあります。それらは「本チュートリアルを学び終えた後」に進むべきステップアップの方向です。

- **Spring Security / JWT 登录鉴权**：现在的 `task-manager` 项目里，任何人都能调用任意接口，没有"登录"和"权限"的概念。Spring Security 负责解决"谁能访问哪个接口"，JWT 是一种常见的"证明你已登录"的令牌方案。之所以现在不学，是因为它涉及过滤器链、认证/授权等一整套新概念，放在入门阶段会喧宾夺主。<br><span class="ja-inline">🇯🇵 **Spring Security / JWT によるログイン認証・認可**：今の `task-manager` プロジェクトでは、誰でも任意の API を呼び出すことができ、「ログイン」や「権限」という概念がありません。Spring Security は「誰がどの API にアクセスできるか」を解決する役割を担い、JWT（JSON Web Token）は「ログイン済みであることを証明する」ための代表的なトークン方式です。今の段階で学ばない理由は、フィルターチェーンや認証・認可といった新しい概念一式が絡んでくるため、入門段階で扱うと本筋を見失わせてしまうからです。</span>
- **Bean 生命周期扩展点**（`@PostConstruct`/`@PreDestroy`、`BeanPostProcessor` 等）：第 16 章讲 Bean 的时候特意降低了深度，只讲了"扫描 → 创建 → 注入 → 使用"这条主线。真实框架源码、中间件开发经常要用到生命周期扩展点做初始化/清理逻辑，属于往"框架原理"方向深挖的内容。<br><span class="ja-inline">🇯🇵 **Bean のライフサイクル拡張ポイント**（`@PostConstruct`/`@PreDestroy`、`BeanPostProcessor` など）：第16章で Bean を説明したときは、あえて深さを抑え、「スキャン → 作成 → 注入 → 使用」という本筋だけを扱いました。実際のフレームワークのソースコードやミドルウェア開発では、初期化・後片付けのロジックにライフサイクル拡張ポイントがよく使われます。これは「フレームワークの仕組み」の方向へさらに掘り下げる内容です。</span>
- **复杂分页性能优化**（COUNT 优化、深分页、游标分页）：第 37 章的分页只解决了"会用、看得懂返回结构"，数据量到百万级之后，`LIMIT` 分页会变慢，需要专门的优化手段，这属于数据库调优范畴，入门阶段不必纠结。<br><span class="ja-inline">🇯🇵 **複雑なページネーションのパフォーマンスチューニング**（COUNT の最適化、深いページ送り、カーソルページネーションなど）：第37章のページネーションは「使える、返ってくる構造が読める」ところまでしか扱っていません。データ量が百万件規模になると `LIMIT` によるページネーションは遅くなり、専用の最適化手段が必要になります。これはデータベースのチューニングの領域であり、入門段階では気にしすぎる必要はありません。</span>
- **Redis 缓存**：真实项目里，频繁查询但不常变化的数据（比如用户信息）通常会缓存到 Redis 里，减少数据库压力。这需要先理解"缓存一致性"这个新问题（数据改了、缓存要不要跟着改），暂不涉及。<br><span class="ja-inline">🇯🇵 **Redis キャッシュ**：実際のプロジェクトでは、頻繁に検索されるがあまり変化しないデータ（ユーザー情報など）は通常 Redis にキャッシュし、データベースへの負荷を減らします。これには「キャッシュの一貫性」という新しい問題（データが変わったらキャッシュも追随して変えるべきか）を先に理解する必要があり、今回は扱いません。</span>
- **完整单元测试体系（Mockito / Testcontainers）**：第 37 章的测试例子里已经用到了一点点 `@MockitoBean`，但完整的 Mockito 用法（`when().thenReturn()`、参数匹配器、验证调用次数）以及 Testcontainers（测试时用容器启动一个真实的、临时的数据库）是更系统的测试工程能力，值得单独花时间学。<br><span class="ja-inline">🇯🇵 **本格的な単体テスト体系（Mockito / Testcontainers）**：第37章のテスト例ではすでに少しだけ `@MockitoBean` を使いましたが、Mockito のフルセットの使い方（`when().thenReturn()`、引数マッチャー、呼び出し回数の検証）や Testcontainers（テスト時にコンテナで実際の一時的なデータベースを起動する仕組み）は、より体系的なテスト工学の能力であり、別途時間をかけて学ぶ価値があります。</span>
- **Docker 容器化部署**：现在项目是在你自己电脑上跑起来的，真实上线需要把项目和它依赖的环境（JDK、数据库等）打包成标准化的容器镜像，方便在任何服务器上一致地运行，这是运维/部署方向的入门知识。<br><span class="ja-inline">🇯🇵 **Docker によるコンテナ化デプロイ**：今のプロジェクトはあなた自身のパソコンで動いていますが、実際に本番稼働させるには、プロジェクトとそれが依存する環境（JDK、データベースなど）を標準化されたコンテナイメージにパッケージ化し、どのサーバーでも同じように動かせるようにする必要があります。これは運用・デプロイ方向の入門知識です。</span>
- **CI/CD**（持续集成/持续部署）：代码提交后自动跑测试、自动构建、自动部署到服务器，是团队协作项目的标配流程，涉及 Git（第 34 章已经打了基础）之外的更多工具链知识。<br><span class="ja-inline">🇯🇵 **CI/CD**（継続的インテグレーション／継続的デリバリー）：コードをコミットした後、自動でテストを実行し、自動でビルドし、自動でサーバーにデプロイする——これはチーム開発プロジェクトの標準的なフローであり、Git（第34章ですでに基礎を学びました）以外の、より多くのツールチェーンの知識が関わってきます。</span>
- **微服务方向**：当一个项目大到一个团队管不过来时，会拆分成多个独立部署、通过网络互相调用的小服务（微服务）。这涉及服务注册发现、远程调用、分布式事务等一整套新问题，是"单体应用"学扎实之后才值得考虑的方向。<br><span class="ja-inline">🇯🇵 **マイクロサービスの方向**：プロジェクトが大きくなりすぎて一つのチームでは管理しきれなくなると、独立してデプロイされ、ネットワーク越しに互いを呼び出す小さなサービス（マイクロサービス）に分割することがあります。これにはサービスの登録・発見、リモート呼び出し、分散トランザクションといった新しい問題一式が関わってきます。「モノリシックなアプリケーション」をしっかり学んだ後に検討する価値のある方向です。</span>

这些方向没有先后顺序的硬性要求，可以根据你实际遇到的需求（比如面试要求、工作任务）挑感兴趣的先深入。

> 🇯🇵 これらの方向には厳密な優先順位はありません。あなたが実際に直面するニーズ（例えば面接で求められること、仕事のタスクなど）に応じて、興味のあるものから深めていけばよいでしょう。

## 结语 ／ おわりに

学完一门技术最好的方式不是收藏更多教程，而是拿一个能跑起来的项目，不断给它加功能、不断把它写"坏"再修好。建议你就用第 37 章的 `task-manager` 项目作为练手起点，试着自己加一些功能，比如：

> 🇯🇵 一つの技術を学び終えた後の最良の方法は、チュートリアルをさらに集める（コレクションする）ことではなく、実際に動くプロジェクトを手元に置き、機能を追加し続け、時には「壊して」はまた直す、を繰り返すことです。第37章の `task-manager` プロジェクトを練習の出発点として、自分で機能を追加してみることをおすすめします。例えば以下のようなものです。

- 给任务加一个"分类"（Category）概念，做一次新的多表关联练习；<br><span class="ja-inline">🇯🇵 タスクに「カテゴリ」（Category）という概念を追加し、新しい複数テーブル関連の練習をしてみる。</span>
- 给任务加一个"截止日期"（dueDate）字段，再做一个"查询即将过期任务"的接口；<br><span class="ja-inline">🇯🇵 タスクに「期限」（dueDate）フィールドを追加し、さらに「まもなく期限が切れるタスクを検索する」API を作ってみる。</span>
- 做一次真正的多表关联查询——比如"查询某个用户的所有任务，同时把用户名一起返回"，体会一下比单表分页更复杂一点的查询场景怎么设计。<br><span class="ja-inline">🇯🇵 本格的な複数テーブル関連クエリを一度やってみる——例えば「あるユーザーの全タスクを検索し、同時にユーザー名も一緒に返す」といった、単一テーブルのページネーションより少し複雑なクエリのシーンをどう設計するか体験してみる。</span>

祝你在 Java Web 开发的路上越走越顺。
