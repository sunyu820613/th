# 第 13 章　从 Servlet 到 MVC ／ 第13章　ServletからMVCへ

## 本章目标 ／ 本章の目標
理解纯 Servlet 写法在项目变大之后会遇到的具体痛点；明白为什么需要一个"统一入口"来分发请求，为什么需要把"业务逻辑"和"页面展示"分开；为后面学习 MVC 模式做铺垫。

> 🇯🇵 純粋なServletの書き方が、プロジェクトが大きくなった後に直面する具体的な問題点を理解します。なぜ「統一された入口」でリクエストを振り分ける必要があるのか、なぜ「ビジネスロジック」と「ページ表示」を分ける必要があるのかを理解します。この先MVCパターンを学ぶための布石とします。

## 一句话理解 ／ 一言で理解する
一个 Servlet 处理一个 URL，页面一多，你就要写一堆结构几乎一样、只是内容不同的类——这种"重复"本身，就是在提醒你：应该有更好的组织方式。

> 🇯🇵 1つのServletが1つのURLを処理します。ページが増えると、構造がほぼ同じで内容だけが違うクラスをたくさん書くことになります——この「重複」そのものが、もっと良い組織の仕方があるはずだと教えてくれているのです。

## 为什么需要它 ／ なぜ必要なのか
上一章结尾留了一个思考题：如果网站有 50 个页面，要写多少个 Servlet？答案是至少 50 个类，而且每个类内部还会重复大量相似的代码。这一章我们把这个问题摊开讲清楚，不是为了批评 Servlet 写法"不好"（它在历史上、在理解原理上都非常有价值），而是为了让你亲身体会"为什么后面要学 MVC、要学 Spring MVC"——任何一个新技术的出现，都是为了解决某个具体的痛点，而不是"因为它更时髦"。

> 🇯🇵 前章の最後に考える問題を残しました——もしサイトに50個のページがあったら、Servletをいくつ書く必要があるでしょうか？答えは少なくとも50個のクラスで、しかも各クラスの内部にも大量の似たようなコードが重複します。本章ではこの問題を丁寧に解きほぐしていきます。それはServletの書き方が「良くない」と批判するためではなく（それは歴史的にも、原理を理解する上でも非常に価値があります）、あなた自身に「なぜこの先MVC、Spring MVCを学ぶ必要があるのか」を体感してもらうためです——どんな新しい技術の登場も、何か具体的な問題を解決するためであり、「より流行っているから」ではありません。

## 核心概念 ／ コアコンセプト

我们先假设一个具体场景：一个小型电商网站，需要下面这些页面/接口：

> 🇯🇵 まず具体的な場面を想定してみましょう。小規模なECサイトが、次のようなページ／APIを必要としているとします。

- 查看用户列表<br><span class="ja-inline">🇯🇵 ユーザー一覧の閲覧</span>
- 查看用户详情<br><span class="ja-inline">🇯🇵 ユーザー詳細の閲覧</span>
- 新增用户<br><span class="ja-inline">🇯🇵 ユーザーの新規追加</span>
- 修改用户<br><span class="ja-inline">🇯🇵 ユーザーの変更</span>
- 删除用户<br><span class="ja-inline">🇯🇵 ユーザーの削除</span>
- 查看商品列表<br><span class="ja-inline">🇯🇵 商品一覧の閲覧</span>
- 查看商品详情<br><span class="ja-inline">🇯🇵 商品詳細の閲覧</span>
- ……（商品、订单、购物车，每个业务对象都要重复一遍类似的增删改查）<br><span class="ja-inline">🇯🇵 ……（商品、注文、ショッピングカートなど、各業務オブジェクトごとに似たようなCRUDを繰り返す必要があります）</span>

按纯 Servlet 的写法，你大概会写出这样的结构：

> 🇯🇵 純粋なServletの書き方に従うと、おそらく次のような構造になるでしょう。

```
UserListServlet      @WebServlet("/users")
UserDetailServlet     @WebServlet("/users/detail")
UserAddServlet        @WebServlet("/users/add")
UserUpdateServlet     @WebServlet("/users/update")
UserDeleteServlet     @WebServlet("/users/delete")
ProductListServlet    @WebServlet("/products")
ProductDetailServlet  @WebServlet("/products/detail")
... 以此类推
```

哪怕只做"用户"和"商品"两个业务对象的基础增删改查，就已经写了 10 个类。这就是**第一个痛点：类的数量随着页面数量线性增长，写不完，也记不住**。

> 🇯🇵 「ユーザー」と「商品」という2つの業務オブジェクトの基本的なCRUDだけでも、すでに10個のクラスを書いています。これが**1つ目の問題点：クラスの数がページ数に比例して増え続け、書ききれず、覚えきれない**ということです。

## 图解 ／ 図解

把其中一个 Servlet 的内部结构画出来，看看每个类里实际都在干什么：

> 🇯🇵 その中の1つのServletの内部構造を描いてみて、各クラスが実際に何をしているのか見てみましょう。

```
UserAddServlet.doPost(req, resp)
  │
  ├─① 从 req 里手动取出参数
  │     String name = req.getParameter("name");
  │     String email = req.getParameter("email");
  │
  ├─② 手动校验参数
  │     if (name == null || name.isEmpty()) { ...返回错误提示... }
  │     if (!email.contains("@")) { ...返回错误提示... }
  │
  ├─③ 手动写业务逻辑（比如保存到某个 List 或数据库）
  │     userList.add(new User(name, email));
  │
  └─④ 手动拼 HTML 字符串，写回响应
        resp.getWriter().println("<html>...新增成功...</html>");
```

现在想象一下：`UserUpdateServlet`、`ProductAddServlet` 里的 ①②④ 这三步，代码结构几乎一模一样，只是取的字段名、校验规则、拼的 HTML 内容不同。**第二个痛点**由此浮现：**"取参数"、"校验参数"、"拼页面"这些通用逻辑，在每个 Servlet 里都被重复写了一遍**。

> 🇯🇵 ここで想像してみてください。`UserUpdateServlet` や `ProductAddServlet` の中の①②④の3ステップは、コード構造がほぼ同じで、取得するフィールド名、検証ルール、組み立てるHTML内容だけが違います。ここから**2つ目の問題点**が浮かび上がります——**「パラメータの取得」「パラメータの検証」「ページの組み立て」といった共通のロジックが、各Servletで繰り返し書かれている**ということです。

再往深处看，还有**第三个痛点**：一个 Servlet 类里，同时塞进了"业务逻辑怎么处理数据"（比如怎么保存用户）和"页面长什么样"（拼 HTML 字符串）这两件完全不同的事情。这两件事变化的原因不一样——业务逻辑可能因为需求调整而改，页面样式可能因为美工改版而改——但纯 Servlet 写法把它们硬揉在同一个方法里，谁都不敢轻易动这个类，改一点点都可能牵连另一部分。

> 🇯🇵 さらに深く見ていくと、**3つ目の問題点**もあります——1つのServletクラスの中に、「業務ロジックがどうデータを処理するか」（例えばどうやってユーザーを保存するか）と「ページがどんな見た目か」（HTML文字列の組み立て）という、まったく異なる2つのことが同時に詰め込まれているのです。この2つのことが変わる理由は異なります——業務ロジックは要件の調整によって変わり、ページのスタイルはデザインの改版によって変わります——しかし純粋なServletの書き方はこれらを同じメソッドの中に無理やり押し込んでいるため、誰もこのクラスを気軽に変更する気になれず、少し変えるだけでも他の部分に影響が及ぶ可能性があります。

## 最小示例 ／ 最小限のサンプル

用一段更接近真实的伪代码，展示"职责混乱"具体长什么样（这段代码只是用来说明问题，不要求能直接编译运行）：

> 🇯🇵 より実際に近い擬似コードを使って、「責務の混乱」が具体的にどのような形をしているかを示します（このコードは問題を説明するためだけのもので、そのままコンパイル・実行できることは求めていません）。

```java
@WebServlet("/users/add")
public class UserAddServlet extends HttpServlet {

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {

        // 第 1 件事：从请求里取参数（重复劳动）
        String name = req.getParameter("name");
        String email = req.getParameter("email");

        // 第 2 件事：手动校验（重复劳动，还容易漏校验）
        if (name == null || name.trim().isEmpty()) {
            resp.getWriter().println("<p>姓名不能为空</p>");
            return;
        }

        // 第 3 件事：业务逻辑（这才是这个 Servlet 真正独有的部分）
        User user = new User(name, email);
        userRepository.save(user);

        // 第 4 件事：手动拼 HTML（和业务逻辑混在一起，页面一改就要动这个类）
        resp.setContentType("text/html;charset=UTF-8");
        resp.getWriter().println("<html><body>");
        resp.getWriter().println("<h1>新增成功：" + name + "</h1>");
        resp.getWriter().println("</body></html>");
    }
}
```

## 代码逐行解释 ／ コードの行ごとの解説

对照上面这段伪代码，逐段说明问题出在哪里：

> 🇯🇵 上記の擬似コードと照らし合わせながら、問題がどこにあるのかを段落ごとに説明します。

- 第 1 件事（取参数）：`req.getParameter(...)` 这种写法，在每一个需要接收表单/参数的 Servlet 里都会重复出现，而且字段一多，容易漏取或者拼错参数名，编译器也帮不了你——因为 `getParameter` 返回的永远是 `String`，取错了名字只会在运行时才发现拿到 `null`。<br><span class="ja-inline">🇯🇵 1つ目のこと（パラメータの取得）：`req.getParameter(...)` というこの書き方は、フォームやパラメータを受け取る必要のあるすべてのServletで繰り返し現れます。しかもフィールドが増えると、取得漏れやパラメータ名のスペルミスが起こりやすく、コンパイラも助けてはくれません——なぜなら `getParameter` が返すのは常に `String` であり、名前を間違えても実行時に `null` を受け取って初めて気づくからです。</span>
- 第 2 件事（校验）：校验逻辑散落在每个 Servlet 内部，没有统一的地方管理，容易有的 Servlet 校验严格、有的 Servlet 忘了校验，规则不一致。<br><span class="ja-inline">🇯🇵 2つ目のこと（検証）：検証ロジックが各Servletの内部にバラバラに存在し、統一して管理する場所がありません。あるServletは検証が厳しく、あるServletは検証を忘れている、といったようにルールが一致しなくなりがちです。</span>
- 第 3 件事（业务逻辑）：这才是这个类真正应该关心的核心内容——"新增一个用户"这件事本身。<br><span class="ja-inline">🇯🇵 3つ目のこと（業務ロジック）：これこそがこのクラスが本来関心を持つべき核心的な内容です——「ユーザーを新規追加する」ということそのものです。</span>
- 第 4 件事（拼 HTML）：把页面展示的细节（标签、样式、文字）和业务逻辑写在同一个方法体里，业务逻辑的开发者和页面样式的调整者互相干扰，谁都不敢单独改这个类而不影响另一半。<br><span class="ja-inline">🇯🇵 4つ目のこと（HTMLの組み立て）：ページ表示の詳細（タグ、スタイル、文言）と業務ロジックを同じメソッドの中に書いてしまうと、業務ロジックの開発者とページスタイルの調整者が互いに干渉し合い、誰もこのクラスを片方だけ単独で変更する気になれなくなります。</span>

这四件事混在一起，正是"职责不清"的具体表现：**一个方法承担了太多不相关的职责**。

> 🇯🇵 この4つのことが混ざり合っているのは、まさに「責務が不明瞭」であることの具体的な現れです——**1つのメソッドがあまりにも多くの無関係な責務を背負っている**のです。

## 程序运行过程 ／ プログラムの実行の流れ

这一章重点不是跑一段代码，而是理清"问题是怎么随着项目变大而暴露出来的"这条逻辑链：

> 🇯🇵 本章の重点はコードを動かすことではなく、「問題がプロジェクトの拡大に伴ってどのように表面化するか」という論理の連鎖を整理することです。

1. 项目刚开始只有 1、2 个页面时，每个页面写一个 Servlet，代码量不大，问题不明显。<br><span class="ja-inline">🇯🇵 プロジェクトが始まったばかりで1、2個のページしかないとき、各ページごとに1つのServletを書けば、コード量は大きくなく、問題も目立ちません。</span>
2. 页面涨到 10 个、20 个，你发现自己在不断复制粘贴"取参数 → 校验 → 拼 HTML"这几段代码，只是改改字段名。<br><span class="ja-inline">🇯🇵 ページが10個、20個に増えると、「パラメータ取得 → 検証 → HTML組み立て」というこれらのコードを、フィールド名を少し変えるだけでひたすらコピー＆ペーストしている自分に気づきます。</span>
3. 某天产品经理要求"所有页面的错误提示样式统一改一下"，你发现要去几十个 Servlet 里逐个修改拼 HTML 的那几行代码，工作量巨大且容易漏改。<br><span class="ja-inline">🇯🇵 ある日、プロダクトマネージャーから「すべてのページのエラー表示スタイルを統一して変更してほしい」と言われ、数十個のServletの中でHTMLを組み立てている行を1つずつ修正しなければならないことに気づきます。作業量は膨大で、変更漏れも起きやすくなります。</span>
4. 某天需要给"新增用户"加一条新的校验规则，你发现business逻辑和页面拼接代码写在一起，改动业务逻辑时不小心可能牵连到页面输出的格式。<br><span class="ja-inline">🇯🇵 ある日「ユーザー新規追加」に新しい検証ルールを追加する必要が生じ、業務ロジックとページ組み立てのコードが一緒に書かれているため、業務ロジックを変更する際に不注意でページ出力のフォーマットにまで影響してしまうことに気づきます。</span>
5. 于是自然会想：**能不能有一个统一的入口，先把"取参数、校验"这类通用工作做掉，再把真正的业务逻辑单独抽出来管理，页面展示也单独交给专门的部分处理？**<br><span class="ja-inline">🇯🇵 そこで自然にこう考えるようになります——**統一された入口を用意して、「パラメータの取得、検証」といった共通の作業を先に片付け、本当の業務ロジックは別に取り出して管理し、ページ表示も専門の部分に任せられないだろうか？**</span>

这个"统一的入口"，后面学 Spring MVC 时你会看到框架已经把它写好了，就是 **DispatcherServlet**——这里先理解"为什么需要它"，具体它是怎么实现的，留到第 20 章详细讲。

> 🇯🇵 この「統一された入口」は、後でSpring MVCを学ぶときに、フレームワークがすでに用意してくれていることが分かります。それが **DispatcherServlet**（ディスパッチャーサーブレット）です——ここではまず「なぜそれが必要なのか」を理解しておき、具体的にどう実現されているかは第20章で詳しく説明します。

1. 主要是：类的数量随页面数量线性增长；取参数、校验、拼页面这类通用代码在多个 Servlet 里重复出现；业务逻辑和页面展示混在同一个方法里，职责不清、维护困难。<br><span class="ja-inline">🇯🇵 主に次の通りです。クラスの数がページ数に比例して増え続けること、パラメータ取得・検証・ページ組み立てといった共通コードが複数のServletで重複して現れること、業務ロジックとページ表示が同じメソッドに混在していて責務が不明瞭で保守が困難になることです。</span>
2. 统一分发入口要解决的是：所有请求先经过同一个地方，由它统一处理一些通用工作（比如找到该由谁处理这个请求），再把真正的业务处理转交出去，避免每个处理单元各自为政、重复劳动。<br><span class="ja-inline">🇯🇵 統一された振り分けの入口が解決しようとしているのは、すべてのリクエストがまず同じ場所を通り、そこが共通の作業（例えば誰がこのリクエストを処理すべきか見つけること）を統一的に処理し、本当の業務処理を引き渡すことで、各処理単位がばらばらに動いて重複作業をしてしまうのを避けることです。</span>
3. `DispatcherServlet`，具体实现原理会在第 20 章详细讲解。<br><span class="ja-inline">🇯🇵 `DispatcherServlet` です。具体的な実装原理は第20章で詳しく説明します。</span>
