# 第 34 章　Git 基础 ／ 第34章　Gitの基礎

## 本章目标 ／ 本章の目標
掌握 `clone`、`status`、`add`、`commit`、`pull`、`push`、分支创建与切换这几个最常用的 Git 命令，能够参与正常的团队协作开发。

> 🇯🇵 `clone`、`status`、`add`、`commit`、`pull`、`push`、ブランチ（branch、開発の分岐線）の作成と切り替えといった、Git（バージョン管理ツール）で最もよく使われるコマンドを身につけ、通常のチーム協働開発に参加できるようになります。

## 一句话理解 ／ 一言で理解する
Git 是一个"记录代码每一次变化"的工具：每次你觉得"这一步改动值得保存"，就执行一次 `commit`，Git 就会把当前所有文件的状态拍一张"快照"存起来，以后随时能看到历史、能和同事互相同步这些快照。

> 🇯🇵 Git は「コードの変化を毎回記録する」ツールです。「この変更は保存する価値がある」と思うたびに `commit` を実行すれば、Git はその時点の全ファイルの状態の「スナップショット」を撮って保存してくれます。あとからいつでも履歴を見たり、同僚とこれらのスナップショットを同期し合ったりできます。

**下载地址**：https://git-scm.com/downloads ，按操作系统选择对应安装包（Windows 版自带一个叫 Git Bash 的命令行工具，装完之后本章的命令都可以在里面运行）。IntelliJ IDEA 内置了图形化的 Git 操作面板，装好 Git 之后也能直接在 IDEA 里点按钮完成大部分操作，不一定非要敲命令。

> 🇯🇵 **ダウンロード先**：https://git-scm.com/downloads 。使用している OS に合わせてインストーラーを選んでください（Windows 版には Git Bash という名前のコマンドラインツールが付属しており、インストール後は本章のコマンドを全てその中で実行できます）。IntelliJ IDEA には Git 操作用のグラフィカルなパネルが内蔵されており、Git をインストールした後は IDEA 上でボタンをクリックするだけで大半の操作を完了できます。必ずしもコマンドを打つ必要はありません。

## 为什么需要它 ／ なぜ必要なのか

`task-manager` 这样的项目，实际工作中通常不是一个人从头写到尾，而是几个人同时在改同一份代码：有人在写 `TaskController`，有人在写 `UserService`，还有人在修一个 Bug。如果没有版本控制工具，大家只能通过来回发送压缩包、手动合并代码来协作，极其容易互相覆盖、丢失修改。

> 🇯🇵 `task-manager` のようなプロジェクトは、実際の仕事では普通、一人が最初から最後まで書くのではなく、複数人が同じコードを同時に変更します。ある人は `TaskController` を書いていて、別の人は `UserService` を書いていて、さらに別の人はバグを修正している——というように。バージョン管理ツールがなければ、みんな圧縮ファイルをやり取りして手動でコードをマージするしかなく、互いの変更を上書きしたり失ったりしやすくなります。

Git 解决的就是这个问题：它能记录每个人的每一次改动，知道"谁在什么时候改了什么"，并且提供了一套机制，让多人对同一份代码的修改能够被合并到一起。本章只讲能让你"正常参与团队协作"所需的最基础命令，不涉及 `rebase`、`cherry-pick` 这类进阶操作——那些留到你实际工作中遇到具体场景再学也不迟。

> 🇯🇵 Git が解決するのはまさにこの問題です。Git は各人の変更を一つ一つ記録し、「誰がいつ何を変更したか」を把握でき、複数人が同じコードに加えた変更を一つに統合するための仕組みを提供します。本章では「正常にチーム協働に参加する」ために必要な最も基礎的なコマンドだけを扱い、`rebase` や `cherry-pick` といった発展的な操作には触れません——それらは実際の仕事で具体的な場面に出会ってから学んでも遅くありません。

## 核心概念 ／ コアコンセプト

| 概念 ／ 概念 | 含义 ／ 意味 |
|---|---|
| 仓库（Repository，简称 repo） | 一个被 Git 管理起来的项目文件夹，里面有一个隐藏的 `.git` 目录记录所有历史<br><span class="ja-inline">🇯🇵 リポジトリ（Repository、略して repo）：Git によって管理されているプロジェクトフォルダ。中には全履歴を記録する隠しディレクトリ `.git` がある </span>|
| 远程仓库（Remote） | 托管在服务器上的仓库（比如 GitHub），团队共享的"中心版本"<br><span class="ja-inline">🇯🇵 リモートリポジトリ（Remote）：サーバー上でホストされているリポジトリ（GitHub など）。チームで共有する「中心となるバージョン」 </span>|
| 本地仓库（Local） | 你电脑上的那一份仓库<br><span class="ja-inline">🇯🇵 ローカルリポジトリ（Local）：自分のパソコン上にあるリポジトリ </span>|
| 工作区（Working Directory） | 你当前正在编辑的文件<br><span class="ja-inline">🇯🇵 作業ディレクトリ（Working Directory）：現在編集しているファイル </span>|
| 暂存区（Staging Area） | `git add` 之后、`git commit` 之前的一个"待提交"区域<br><span class="ja-inline">🇯🇵 ステージングエリア（Staging Area）：`git add` の後、`git commit` の前にある「コミット待ち」の領域 </span>|
| 提交（Commit） | 一次"快照"，记录了这次改动了哪些内容、谁改的、什么时候改的<br><span class="ja-inline">🇯🇵 コミット（Commit）：一回の「スナップショット」で、今回何を変更したか、誰が、いつ変更したかを記録する </span>|
| 分支（Branch） | 一条独立的开发线，可以在不影响主线代码的情况下并行开发某个功能<br><span class="ja-inline">🇯🇵 ブランチ（Branch）：独立した開発ラインで、メインラインのコードに影響を与えずに特定の機能を並行して開発できる </span>|

## 图解 ／ 図解

```
工作区（你正在改的文件）
      │  git add
      ▼
暂存区（准备好要提交的内容）
      │  git commit
      ▼
本地仓库（保存好的历史快照）
      │  git push
      ▼
远程仓库（团队共享，比如 GitHub 上的仓库）
      ▲
      │  git pull
本地仓库（把别人推送上去的最新内容拉下来）
```

## 最小示例 ／ 最小限のサンプル

以下每条命令给出用途说明，均在项目根目录（`task-manager/` 内）执行。

> 🇯🇵 以下の各コマンドには用途の説明を付けています。いずれもプロジェクトのルートディレクトリ（`task-manager/` の中）で実行します。

```bash
# 1. 把远程仓库完整复制一份到本地，初次加入一个项目时用
git clone https://github.com/your-team/task-manager.git

# 2. 查看当前工作区里哪些文件被修改了、哪些还没提交
git status

# 3. 把某个文件的改动放入暂存区，准备提交
git add src/main/java/com/example/taskmanager/controller/TaskController.java

# 3'. 把所有改动过的文件一次性都加入暂存区（更常用）
git add .

# 4. 把暂存区的内容正式提交为一次快照，-m 后面写这次改动的说明
git commit -m "新增任务分页查询接口"

# 5. 把本地新提交的快照推送到远程仓库，让团队其他人也能看到
git push

# 6. 把远程仓库上别人推送的最新改动拉取到本地，和自己的代码合并
git pull

# 7. 基于当前分支创建一个新分支，专门开发某个功能
git branch feature/task-pagination

# 8. 切换到刚才创建的分支上工作
git checkout feature/task-pagination

# 7+8 也可以合并成一条命令：创建并立即切换到新分支
git checkout -b feature/task-pagination
```

## 代码逐行解释 ／ コードの行ごとの解説

- `git clone <地址>`：只在第一次拿到一个项目时用一次，之后就在本地仓库里正常工作，不需要重复 `clone`。<br><span class="ja-inline">🇯🇵 `git clone <URL>`：プロジェクトを初めて手に入れるときに一度だけ使います。その後はローカルリポジトリで通常通り作業すればよく、`clone` を繰り返す必要はありません。</span>
- `git status`：几乎是使用频率最高的命令，随时看一眼"我现在改了什么、还有什么没提交"，能有效避免"忘了提交某个文件"的情况。<br><span class="ja-inline">🇯🇵 `git status`：ほぼ最も使用頻度の高いコマンドです。「今何を変更したか、まだコミットしていないものは何か」をいつでも確認でき、「あるファイルのコミットを忘れる」という事態を効果的に防げます。</span>
- `git add`：把修改从"工作区"移到"暂存区"，可以理解成"选中这些改动，准备打包"。可以精确到单个文件，也可以用 `.` 一次性选中所有改动。<br><span class="ja-inline">🇯🇵 `git add`：変更を「作業ディレクトリ」から「ステージングエリア」へ移します。「これらの変更を選択して、パッケージ化する準備をする」と理解できます。個々のファイルを指定することもできますし、`.` で全ての変更を一度に選択することもできます。</span>
- `git commit -m "..."`：把暂存区里的内容正式打包成一次提交，`-m` 后面的说明文字非常重要——团队协作时，清晰的提交说明能让别人（包括未来的自己）一眼看懂这次改动是干什么的。<br><span class="ja-inline">🇯🇵 `git commit -m "..."`：ステージングエリアの内容を正式に一回のコミットとしてパッケージ化します。`-m` の後ろの説明文はとても重要です——チーム協働では、分かりやすいコミットメッセージによって、他の人（未来の自分も含む）が今回の変更が何をしたのか一目で理解できます。</span>
- `git push`：把本地的提交同步到远程仓库，团队其他成员才能看到你的改动。<br><span class="ja-inline">🇯🇵 `git push`：ローカルのコミットをリモートリポジトリに同期します。これでチームの他のメンバーもあなたの変更を見られるようになります。</span>
- `git pull`：把远程仓库上（可能是同事推送的）最新提交同步到本地，实际上是 `git fetch`（下载）加 `git merge`（合并）两步的组合，本教程不展开这两步的细节。<br><span class="ja-inline">🇯🇵 `git pull`：リモートリポジトリ上の（同僚が push したかもしれない）最新のコミットをローカルに同期します。実際には `git fetch`（ダウンロード）と `git merge`（マージ）の2ステップを組み合わせたものですが、本チュートリアルではこの2ステップの詳細には触れません。</span>
- `git branch <分支名>`：创建一个新分支，此时并不会自动切换过去。<br><span class="ja-inline">🇯🇵 `git branch <ブランチ名>`：新しいブランチを作成しますが、このとき自動的にそのブランチへ切り替わるわけではありません。</span>
- `git checkout <分支名>`：切换到指定分支；`git checkout -b <分支名>` 是"创建并切换"的简写，团队开发中给自己要做的功能单独开一个分支是非常常见的习惯，可以避免直接在主分支（通常叫 `main` 或 `master`）上修改，减少互相影响。<br><span class="ja-inline">🇯🇵 `git checkout <ブランチ名>`：指定したブランチへ切り替えます。`git checkout -b <ブランチ名>` は「作成して切り替える」の省略形です。チーム開発では、自分が担当する機能ごとに専用のブランチを作るのが非常に一般的な習慣で、メインブランチ（通常 `main` や `master` と呼ばれる）を直接変更することを避け、互いへの影響を減らせます。</span>

## 程序运行过程 ／ プログラムの実行の流れ

Git 的命令不涉及 HTTP/Servlet/Spring MVC 调用链，这里改用一个团队协作的典型场景，串一遍本章命令的执行顺序：

> 🇯🇵 Git のコマンドは HTTP/Servlet/Spring MVC の呼び出しチェーンとは関係がないため、ここではチーム協働の典型的なシナリオを使って、本章のコマンドの実行順序を一通りたどってみます。

1. 小明第一次加入 `task-manager` 项目，执行 `git clone` 把仓库完整复制到本地。<br><span class="ja-inline">🇯🇵 小明さんが初めて `task-manager` プロジェクトに参加し、`git clone` を実行してリポジトリを丸ごとローカルにコピーします。</span>
2. 小明想开发"任务分页"功能，先执行 `git checkout -b feature/task-pagination` 创建并切换到一个专属分支。<br><span class="ja-inline">🇯🇵 小明さんは「タスクのページネーション」機能を開発したいので、まず `git checkout -b feature/task-pagination` を実行して専用ブランチを作成・切り替えます。</span>
3. 小明修改了 `TaskController.java`，随手执行 `git status` 看一眼，确认改动的文件在预期范围内。<br><span class="ja-inline">🇯🇵 小明さんは `TaskController.java` を変更し、ついでに `git status` を実行して、変更されたファイルが想定範囲内であることを確認します。</span>
4. 确认无误后，执行 `git add .` 把所有改动加入暂存区。<br><span class="ja-inline">🇯🇵 問題ないことを確認した後、`git add .` を実行して全ての変更をステージングエリアに追加します。</span>
5. 执行 `git commit -m "新增任务分页查询接口"`，生成一条本地提交记录。<br><span class="ja-inline">🇯🇵 `git commit -m "新增任务分页查询接口"`（コミットメッセージの意味は「タスクのページネーション検索APIを追加」）を実行し、ローカルのコミット記録を1件作成します。</span>
6. 开发完成，执行 `git push`（首次推送新分支可能需要加上 `-u origin feature/task-pagination` 指定远程分支，这一步在实际操作中命令行通常会有提示）。<br><span class="ja-inline">🇯🇵 開発が完了したら `git push` を実行します（新しいブランチを初めて push する際は `-u origin feature/task-pagination` を付けてリモートブランチを指定する必要があるかもしれません。この点は実際の操作でコマンドラインが通常ヒントを表示してくれます）。</span>
7. 与此同时，同事小红也在开发别的功能并推送到了远程仓库。小明第二天上班，先执行 `git pull` 把小红的最新改动同步到本地，再继续自己的开发。<br><span class="ja-inline">🇯🇵 同時に、同僚の小紅さんも別の機能を開発してリモートリポジトリに push していました。小明さんは翌日出勤したら、まず `git pull` を実行して小紅さんの最新の変更をローカルに同期してから、自分の開発を続けます。</span>

## 常见错误 ／ よくあるエラー

| 现象 ／ 現象 | 原因 ／ 原因 | 解决 ／ 解決方法 |
|---|---|---|
| `git push` 报错，提示远程有更新的提交 | 别人已经推送了新的改动，本地版本落后<br><span class="ja-inline">🇯🇵 他の人がすでに新しい変更を push しており、ローカルのバージョンが古くなっている </span>| 先执行 `git pull` 把远程改动合并到本地，解决完可能出现的冲突后再 `push`<br><span class="ja-inline">🇯🇵 先に `git pull` を実行してリモートの変更をローカルに統合し、発生し得るコンフリクトを解決してから `push` する </span>|
| `git commit` 提示"没有可提交的改动" | 忘了先执行 `git add`<br><span class="ja-inline">🇯🇵 先に `git add` を実行するのを忘れている </span>| 先 `git add`，把改动放入暂存区，再 `commit`<br><span class="ja-inline">🇯🇵 先に `git add` で変更をステージングエリアに入れてから `commit` する </span>|
| 忘记切换分支，直接在主分支上改了代码 | 开发新功能前忘了先 `checkout -b` 一个新分支<br><span class="ja-inline">🇯🇵 新機能を開発する前に `checkout -b` で新しいブランチを作るのを忘れている </span>| 养成"开始写新功能前先建分支"的习惯；已经改了的话，可以先 `commit`，之后再考虑怎样迁移到正确的分支（这属于进阶操作，本章不展开）<br><span class="ja-inline">🇯🇵 「新機能を書き始める前にまずブランチを作る」習慣をつける。すでに変更してしまった場合は、まず `commit` してから、正しいブランチへどう移すか考える（これは発展的な操作であり、本章では扱わない） </span>|

3. 创建一个新分支并切换过去，做一次小改动并提交，再切回原来的分支，观察文件内容是否恢复成切换前的样子。<br><span class="ja-inline">🇯🇵 新しいブランチを作成して切り替え、小さな変更を加えてコミットし、元のブランチに切り戻して、ファイルの内容が切り替え前の状態に戻るかどうか観察しましょう。</span>

2. `git pull` 和 `git push` 的方向分别是什么？<br><span class="ja-inline">🇯🇵 `git pull` と `git push` の方向はそれぞれどうなっていますか？</span>
3. 为什么团队协作时通常建议给新功能单独开一个分支，而不是直接在主分支上改？<br><span class="ja-inline">🇯🇵 なぜチーム協働では、新機能に対して直接メインブランチで変更するのではなく、通常専用のブランチを開くことが推奨されるのですか？</span>

<details>
<summary>参考答案 ／ 解答</summary>

1. `git add` 把工作区里的改动放入暂存区，标记为"准备提交"；`git commit` 把暂存区的内容正式打包成一条历史快照。<br><span class="ja-inline">🇯🇵 `git add` は作業ディレクトリの変更をステージングエリアに入れ、「コミット準備完了」の印を付けます。`git commit` はステージングエリアの内容を正式に1つの履歴スナップショットとしてパッケージ化します。</span>
2. `git pull` 是把远程仓库的最新内容拉取到本地；`git push` 是把本地的提交推送到远程仓库。<br><span class="ja-inline">🇯🇵 `git pull` はリモートリポジトリの最新の内容をローカルに取り込むもので、`git push` はローカルのコミットをリモートリポジトリへ送信するものです。</span>
3. 单独开分支可以在不影响主分支（通常是可随时部署的稳定代码）的情况下开发和试验，出问题也不会牵连到主分支，方便多人并行开发不同功能。<br><span class="ja-inline">🇯🇵 専用のブランチを開くことで、メインブランチ（通常はいつでもデプロイ可能な安定したコード）に影響を与えずに開発や試行ができ、問題が起きてもメインブランチを巻き込みません。複数人が別々の機能を並行して開発するのにも便利です。</span>
</details>
