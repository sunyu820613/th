## 易混概念对照 ／ 混同しやすい概念の対照

| 概念 A ／ 概念A | 概念 B ／ 概念B | 一句话区别 ／ 一言での違い |
|---|---|---|
| `throw` | `throws` | `throw` 写在方法体内部，是**动作**——主动抛出一个具体的异常对象；`throws` 写在方法签名上，是**声明**——告诉调用者"这个方法可能会抛出某种异常"。<br><span class="ja-inline">🇯🇵 `throw` はメソッド本体の中に書く**動作**であり、具体的な例外オブジェクトを能動的にスローする。`throws` はメソッドシグネチャに書く**宣言**であり、呼び出し元に「このメソッドはある種の例外をスローする可能性がある」と伝える。 </span>|
| 方法重载（Overload）<br><span class="ja-inline">🇯🇵 メソッドオーバーロード（Overload） </span>| 方法重写（Override）<br><span class="ja-inline">🇯🇵 メソッドオーバーライド（Override） </span>| 重载发生在**同一个类**内部，方法名相同但参数列表（个数/类型/顺序）不同，编译期根据调用参数决定用哪个；重写发生在**父子类之间**，方法签名必须完全一致，子类重新实现父类的方法，运行期根据对象的实际类型决定执行哪个版本（多态的基础）。<br><span class="ja-inline">🇯🇵 オーバーロードは**同じクラス内**で発生し、メソッド名は同じだが引数リスト（個数／型／順序）が異なり、コンパイル時に呼び出し引数に基づいてどれを使うか決まる。オーバーライドは**親子クラス間**で発生し、メソッドシグネチャは完全に一致させなければならず、子クラスが親クラスのメソッドを再実装し、実行時にオブジェクトの実際の型に基づいてどのバージョンを実行するか決まる（多態性の基礎）。 </span>|
| `List` | 数组（Array）<br><span class="ja-inline">🇯🇵 配列（Array） </span>| 数组长度创建后**固定不变**，用 `.length`（属性）取长度；`List` 长度可以随 `add`/`remove` **自动伸缩**，用 `.size()`（方法）取长度，并且 `List` 需要配合泛型（如 `List<User>`）在编译期做类型检查，而数组本身天然是强类型的（如 `int[]`、`User[]`）。<br><span class="ja-inline">🇯🇵 配列は作成後、長さが**固定され変わらない**。`.length`（属性）で長さを取得する。`List` の長さは `add`/`remove` に伴って**自動的に伸縮する**。`.size()`（メソッド）で長さを取得し、`List` はジェネリクス（`List<User>` など）と組み合わせてコンパイル時の型チェックが必要だが、配列自体は元から強い型付けである（`int[]`、`User[]` など）。 </span>|
| `private` 字段<br><span class="ja-inline">🇯🇵 `private` フィールド </span>| `protected` 字段<br><span class="ja-inline">🇯🇵 `protected` フィールド </span>| `private` 只能在**类自己内部**访问；`protected` 除了类自己，**子类**（即使在不同包）也能直接访问，是为继承关系专门留的"半开放"权限。<br><span class="ja-inline">🇯🇵 `private` は**クラス自身の内部**でしかアクセスできない。`protected` はクラス自身に加えて、**子クラス**（異なるパッケージであっても）も直接アクセスできる、継承関係のために特別に用意された「半開放」の権限である。 </span>|
| `static` 成员<br><span class="ja-inline">🇯🇵 `static` メンバー </span>| 实例成员<br><span class="ja-inline">🇯🇵 インスタンスメンバー </span>| `static` 成员属于**类本身**，所有对象共享同一份，可以直接用"类名.成员名"访问；实例成员属于**每一个具体对象**，每个对象各有一份独立的数据，必须先创建对象才能访问。<br><span class="ja-inline">🇯🇵 `static` メンバーは**クラス自身**に属し、すべてのオブジェクトが同じ1つを共有し、「クラス名.メンバー名」で直接アクセスできる。インスタンスメンバーは**それぞれの具体的なオブジェクト**に属し、各オブジェクトが独自のデータを持ち、オブジェクトを作成して初めてアクセスできる。 </span>|
| `Optional` | 直接判断 `== null`<br><span class="ja-inline">🇯🇵 直接 `== null` で判定する </span>| 两者都能处理"值可能不存在"的情况，但 `Optional` 用类型把"这个值可能没有"这件事显式表达出来，更容易提醒开发者不要遗漏空值处理；`== null` 完全依赖开发者自己记得判断，容易遗漏。<br><span class="ja-inline">🇯🇵 両者とも「値が存在しないかもしれない」状況を処理できるが、`Optional` は型で「この値はないかもしれない」ことを明示的に表現し、開発者にnull値処理を忘れないよう促しやすい。`== null` は完全に開発者が自分で判定を覚えていることに依存し、見落としやすい。 </span>|
| Lambda 表达式<br><span class="ja-inline">🇯🇵 Lambda式 </span>| 匿名内部类<br><span class="ja-inline">🇯🇵 匿名内部クラス </span>| 两者在效果上等价，都是"就地实现一个接口"；Lambda 只能用于**只有一个抽象方法的接口**（函数式接口），写法更简洁；匿名内部类没有这个限制，但写法更啰嗦。<br><span class="ja-inline">🇯🇵 両者は効果として同等であり、どちらも「その場でインターフェースを実装する」ものである。Lambdaは**抽象メソッドが1つだけのインターフェース**（関数型インターフェース）にしか使えないが、書き方はより簡潔である。匿名内部クラスにはこの制限はないが、書き方はより冗長である。 </span>|

## 测试题 ／ テスト問題

1. 下面代码的输出是什么？<br><span class="ja-inline">🇯🇵 次のコードの出力は何ですか？</span>
   ```java
   int score = 82;
   String grade;
   if (score >= 90) {
       grade = "优秀";
   } else if (score >= 75) {
       grade = "良好";
   } else {
       grade = "及格";
   }
   System.out.println(grade);
   ```

2. `for` 循环和 `while` 循环该如何选择？各举一个更适合的业务场景。<br><span class="ja-inline">🇯🇵 `for` ループと `while` ループはどう選択すべきですか？それぞれより適した業務場面を1つずつ挙げてください。</span>

3. 下面代码会抛出什么异常？为什么？<br><span class="ja-inline">🇯🇵 次のコードはどんな例外をスローしますか？その理由も答えてください。</span>
   ```java
   int[] arr = new int[3];
   System.out.println(arr[3]);
   ```

4. 简述构造方法里为什么经常需要写 `this.name = name;` 而不是直接 `name = name;`。<br><span class="ja-inline">🇯🇵 コンストラクタで `name = name;` ではなく `this.name = name;` と書く必要がよくある理由を簡潔に説明してください。</span>

5. 下面代码的输出是什么？说明理由。<br><span class="ja-inline">🇯🇵 次のコードの出力は何ですか？理由も説明してください。</span>
   ```java
   Person p = new Student("小红", 20);
   p.introduce();
   // 假设 Student extends Person，并重写了 introduce()
   ```

6. `List<User> list = new ArrayList();`（右边没有加泛型参数）和 `List<User> list = new ArrayList<>();` 有什么区别？<br><span class="ja-inline">🇯🇵 `List<User> list = new ArrayList();`（右辺にジェネリクスの型引数がない）と `List<User> list = new ArrayList<>();` にはどんな違いがありますか？</span>

7. 一个方法上写了 `@Override`，但实际上编译报错说"方法未覆盖或未实现父类型的方法"，最可能的原因是什么？<br><span class="ja-inline">🇯🇵 あるメソッドに `@Override` を書いたが、実際には「メソッドが親の型のメソッドをオーバーライドまたは実装していません」というコンパイルエラーが出た場合、最も考えられる原因は何ですか？</span>

8. 用一句话解释"注解是什么"，并举一个到目前为止学过的注解例子。<br><span class="ja-inline">🇯🇵 「アノテーションとは何か」を一言で説明し、これまでに学んだアノテーションの例を1つ挙げてください。</span>

<details>
<summary>参考答案 ／ 解答</summary>

1. 输出 `良好`。因为 `82 >= 90` 不成立，跳到 `else if (score >= 75)`，`82 >= 75` 成立，赋值为 `"良好"` 并跳过后面的 `else`。<br><span class="ja-inline">🇯🇵 `良好` が出力されます。`82 >= 90` は成立しないため `else if (score >= 75)` に進み、`82 >= 75` が成立するので `"良好"` が代入され、以降の `else` はスキップされます。</span>

2. 循环次数或范围在写代码时就能确定（比如"遍历数组的每个元素""打印 1 到 100"）更适合用 `for`；循环次数依赖运行时才能知道的条件（比如"不断读取用户输入直到用户选择退出"）更适合用 `while`。<br><span class="ja-inline">🇯🇵 ループ回数や範囲がコードを書く時点で確定している場合（「配列の各要素を巡回する」「1から100まで出力する」など）は `for` がより適しています。ループ回数が実行時になって初めてわかる条件に依存する場合（「ユーザーが終了を選ぶまで入力を読み続ける」など）は `while` がより適しています。</span>

3. 抛出 `ArrayIndexOutOfBoundsException`（数组下标越界异常）。因为 `arr` 长度是 3，合法下标是 `0~2`，访问 `arr[3]` 超出范围。<br><span class="ja-inline">🇯🇵 `ArrayIndexOutOfBoundsException`（配列の添字が範囲外である例外）がスローされます。`arr` の長さは3で、有効な添字は `0~2` であり、`arr[3]` へのアクセスは範囲を超えているからです。</span>

4. 因为构造方法的参数名和字段名相同时，如果不加 `this.`，`name = name;` 会被理解成"参数自己赋值给自己"，字段根本没有被真正赋值；加上 `this.name` 明确表示左边是"当前对象自己的字段"。<br><span class="ja-inline">🇯🇵 コンストラクタの引数名とフィールド名が同じ場合、`this.` を付けなければ `name = name;` は「引数が自分自身に代入する」ものと解釈され、フィールドには実際には値が代入されないからです。`this.name` を付けることで、左辺が「現在のオブジェクト自身のフィールド」であることを明示します。</span>

5. 输出的是 `Student` 重写后 `introduce()` 里的内容。因为 Java 在运行时是根据变量**实际指向的对象类型**（这里是 `Student`）决定调用哪个版本的方法，即使变量声明的类型是父类 `Person`，这就是多态。<br><span class="ja-inline">🇯🇵 出力されるのは `Student` がオーバーライドした `introduce()` の内容です。Javaは実行時に変数が**実際に指すオブジェクトの型**（ここでは `Student`）に基づいてどのバージョンのメソッドを呼び出すか決定するためで、変数の宣言型が親クラス `Person` であってもそうなります。これが多態性です。</span>

6. 右边没写 `<>` 里的类型参数（写成 `new ArrayList()`）是一种"原始类型"用法，编译器只会给出"未检查类型"的警告而不会报错，但会失去泛型在编译期的类型检查能力；写成 `new ArrayList<>()`（钻石语法）编译器会根据左边 `List<User>` 自动推断出这也是一个只能装 `User` 的 `ArrayList`，能获得完整的类型安全检查，是推荐写法。<br><span class="ja-inline">🇯🇵 右辺に `<>` 内の型引数を書かない（`new ArrayList()` と書く）のは「生の型」の使い方であり、コンパイラは「未チェックの型」という警告を出すだけでエラーにはなりませんが、ジェネリクスによるコンパイル時の型チェック能力を失います。`new ArrayList<>()`（ダイヤモンド構文）と書けば、コンパイラは左辺の `List<User>` から自動的にこれも `User` しか入れられない `ArrayList` であると推論し、完全な型安全チェックが得られる推奨の書き方です。</span>

7. 最可能是方法签名和父类（或接口）里的方法不完全一致——比如方法名拼写不同、参数类型或个数不同、参数顺序不同。`@Override` 的作用正是让编译器帮你检查这一点，如果没有真正构成重写，编译器就会在这里报错提醒你。<br><span class="ja-inline">🇯🇵 最も考えられるのは、メソッドシグネチャが親クラス（またはインターフェース）のメソッドと完全に一致していないことです——例えばメソッド名のスペルが異なる、引数の型や個数が異なる、引数の順序が異なる、などです。`@Override` の役割はまさにこの点をコンパイラにチェックさせることであり、本当にオーバーライドが成立していなければ、コンパイラがここでエラーを出して知らせてくれます。</span>

8. 注解是贴在代码（类、方法、字段等）上的一种"标签"，本身不会改变代码的执行逻辑，是否有实际效果取决于有没有工具或框架在特定时机读取这个标签并采取行动。例子：`@Override` 贴在方法上，编译器在编译阶段读取这个标签，检查这个方法是否真的构成了对父类或接口方法的重写。<br><span class="ja-inline">🇯🇵 アノテーションはコード（クラス、メソッド、フィールドなど）に貼る一種の「タグ」であり、それ自体はコードの実行ロジックを変えません。実際に効果があるかどうかは、ツールやフレームワークが特定のタイミングでこのタグを読み取って行動を起こすかどうかにかかっています。例：`@Override` はメソッドに貼られ、コンパイラがコンパイル段階でこのタグを読み取り、このメソッドが本当に親クラスまたはインターフェースのメソッドのオーバーライドを構成しているかチェックします。</span>
</details>
